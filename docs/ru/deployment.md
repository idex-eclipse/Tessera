# Доставка и установка плагинов

Core-плагины (`@core/…`) вшиты в бандл хоста. Remote-плагины доставляются как
файлы на сервере хоста — по аналогии с `klippy/extras` в Klipper: вы кладёте
файлы в папку, хост их находит.

Доставка состоит из четырёх слоёв:

| Слой | Что делает | Где |
|---|---|---|
| **Provisioning** | файлы плагина лежат на сервере | `<проект>/extensions/<имя>/` |
| **Discovery** | список доступных плагинов | `/extensions/index.json` (статический файл) |
| **Loading** | fetch манифеста → import модуля | загрузчик плагинов хоста |
| **Enablement** | включён ли плагин, на каких принтерах | `localStorage` → `mpu:v2:plugins` |

Сам браузер файлы на сервер не пишет: источник истины — содержимое `extensions/`.
Файлы попадают туда тремя путями:

- **из реестра в UI**: Settings → Plugins → **Реестр плагинов**. Работает через
  [службу `tessera-ext`](#служба-tessera-ext-установка-из-ui);
- **из реестра в терминале**: команда `tessera-ext`. Те же проверенные готовые архивы
  со сверкой sha256;
- **вручную**: копируете папку плагина в `extensions/<имя>/` и запускаете
  `tessera-ext sync` (в dev-checkout: `node tools/extensions-sync.cjs`). Для разработки
  и частных плагинов.

## Provisioning

```
extensions/
├── index.json                  ← генерируется tessera-ext sync
├── hello/
│   ├── manifest.json
│   ├── index.js                ← entry (имя берётся из manifest.entry)
│   └── assets/…                ← любые статические файлы плагина
└── another-plugin/
    ├── manifest.json
    └── …
```

Правила:

- Имя папки произвольно, но удобнее делать его совпадающим с коротким именем плагина
  (в URL манифеста оно попадает как `/extensions/<имя>/manifest.json`).
- Обязателен `manifest.json` с полями `id`, `name`, `version`, `entry`.
- `entry` резолвится **относительно URL манифеста**: `"entry": "index.js"` →
  `/extensions/hello/index.js`. Абсолютный URL и путь от корня тоже допустимы.
- Поле `icon` в манифесте необязательно; скрипт пробрасывает его в запись каталога.

### Из реестра плагинов (рекомендуемый путь)

Проверенные плагины публикуются в отдельном репозитории-реестре
[tessera-ext](https://github.com/idex-eclipse/Tessera-Ext): готовый архив `.tar.gz`
на каждую версию и `registry.json` с sha256 архивов (как он пополняется — см.
[Публикация в реестр](#публикация-в-реестр)). На
принтере ничего не собирается: CLI скачивает архив, сверяет хеш и распаковывает его
в `extensions/<dir>/`:

```bash
tessera-ext                     # интерактивное меню: номер = установить / обновить / удалить
tessera-ext list                # плагины реестра + что установлено
tessera-ext install hello       # скачать → sha256 → extensions/hello/
tessera-ext update --all        # или: update hello
tessera-ext remove hello
tessera-ext branch dev          # ветка реестра (и в меню: S) Settings)
```

Команду `tessera-ext` (`/usr/local/bin/tessera-ext`) создаёт `deploy/install.sh`.
Она запускает [`deploy/install-ext.sh`](../../deploy/install-ext.sh), а тот —
`deploy/tessera-ext.py` из каталога установки (системный `python3` ≥ 3.7, только
стандартная библиотека, venv не нужен). Плагин можно назвать полным id
(`acme/hello`) или коротким именем (`hello`); неоднозначное имя — ошибка. Без
команды `tessera-ext` (например, до обновления Tessera) работает
`bash ~/tessera/deploy/install-ext.sh`. В конце `install.sh` предлагает сразу
открыть меню.

`index.json` CLI пересобирает сам. Дальше — Settings → Plugins → Refresh → Install.

Что CLI проверяет, прежде чем что-то попадёт в `extensions/`:

- sha256 архива совпадает с `registry.json`;
- в архиве только обычные файлы и папки: без симлинков, абсолютных путей и `..`;
- архив не больше 20 МБ и распаковывается не больше чем в 100 МБ и 5000 записей;
- `manifest.json` из архива совпадает с записью реестра по `id` и `version`;
- `pluginApi` записи подходит хосту: MAJOR тот же, MINOR не больше хостового (сейчас `0.8`;
  см. [plugin-development.md](plugin-development.md#версия-plugin-api)). Целое `1` старых
  записей означает `0.7`.

Плагин распаковывается в скрытую staging-папку и подменяется через `rename`. Если
обновление не удалось, остаётся прежняя версия. Рядом с манифестом плагина из
реестра появляется файл `.tessera-origin.json`. Папку, положенную вручную, CLI без
`--force` не перезапишет.

**Ветка реестра.** CLI читает `registry/registry.json` из ветки `main` репозитория
`Tessera-Ext`. Другая ветка (например, `dev` с ещё не выпущенными версиями)
выбирается в меню (**S) Settings → Branch**, список веток с GitHub) или командой
`tessera-ext branch <имя>`. Выбор сохраняется в `~/.config/tessera/tessera-ext.conf`
и не зависит от ветки самого Tessera. `TESSERA_EXT_BRANCH` задаёт ветку на один запуск.

`TESSERA_REGISTRY_URL` переопределяет адрес реестра и ветку: `https://`, `file://` или
локальный путь. Локальный путь удобен, чтобы проверить реестр до публикации.

Раздача на сервере:

- **dev** (`npm run dev`): middleware в `vite.config.ts` отдаёт `extensions/` на
  `/extensions/...` с чтением диска на каждый запрос и `Cache-Control: no-cache`
  для `.json` и `.js`.
- **prod**: nginx-блок `location /extensions/ { alias <каталог проекта>/extensions/; … }`
  с отключённым кэшированием (его настраивает `deploy/install.sh`).

Кэширование: сайт nginx из `deploy/install.sh` отдаёт `no-cache, no-store` для всего
`/extensions/`, поэтому браузер получит свежий код при следующей загрузке страницы. На своём
сервере держите `index.json`, `manifest.json` и `entry` без хеша в `no-cache`; файлы с
хешами в имени (`index-3f9a1c.js`) можно кэшировать `immutable`.

## Discovery: каталог

`extensions/index.json` — **статический** массив, который генерирует скрипт:

```bash
tessera-ext sync                # на принтере
node tools/extensions-sync.cjs  # в dev-checkout, тот же формат
```

Команда обходит `extensions/*/manifest.json` и записывает:

```json
[
  {
    "id": "acme/hello",
    "name": "Hello",
    "version": "1.0.0",
    "manifestUrl": "/extensions/hello/manifest.json",
    "icon": "optional",
    "description": "optional",
    "origin": "registry",
    "sha256": "…"
  }
]
```

`origin` равен `registry` у плагинов, установленных из реестра
(в каталоге у них бейдж *Проверен*), и `local` у папок, положенных вручную. Папки,
имя которых начинается с `.`, пропускаются.

Папки без `manifest.json` пропускаются с предупреждением; ошибки разбора
манифеста логируются, остальные плагины всё равно попадают в каталог.

Запускайте её **после добавления плагина вручную** и при смене его `name`/`version`.
Правки кода плагина без смены версии перегенерации не требуют.

Каталог — удобство discovery, не источник истины для загрузки: плагин, которого
нет в `index.json`, всё равно можно установить по URL.

## Установка пользователем

### Из каталога

Settings → Plugins → **Refresh** (перечитывает `index.json` без кэша) →
**Install**. Для каждой записи показывается состояние:

| Состояние | Условие |
|---|---|
| не установлен | нет записи в `mpu:v2:plugins` |
| установлен | запись есть, версия совпадает с каталогом (или не записана) |
| доступно обновление | `installedVersion` ≠ версия в каталоге |

### Из реестра, прямо в UI

Settings → Plugins → **Реестр плагинов**: **Install** скачивает плагин на сервер и сразу
включает его в этом браузере. **Update** обновляет файлы (новый код подхватится после
перезагрузки страницы, UI покажет плашку), **Remove** удаляет файлы и запись. Блок виден,
только если служба доступна; без неё всё работает как раньше, через `tessera-ext`.
Папки, положенные вручную, через UI не заменяются и не удаляются.

### По URL (advanced)

Только этот диалог может ограничить плагин набором принтеров (`printerIds`); пустой список —
все принтеры.

Settings → Plugins → **Добавить по URL (продвинутый режим)**: хост загружает манифест по
адресу, показывает превью (`id`, `name`, `version`) и предупреждение о доверии
(плагин получает полный доступ к Moonraker). Запись получает бейдж *external*.

Для адреса с другого origin сервер плагина должен отдавать **CORS** (и для
манифеста, и для модуля). Для плагинов из `extensions/` (тот же origin) CORS не
нужен.

По умолчанию `deploy/install.sh` **запрещает** этот режим на сервере. nginx отдаёт
`Content-Security-Policy: script-src 'self'`, и браузер не импортирует модуль с
чужого origin. Ещё установщик пишет `/extensions/policy.json`
(`{ "allowRemotePlugins": false }`), и UI прячет кнопку. Если `policy.json` нет
(dev-сервер, ручная настройка), кнопка видна.

Настройка меняется в меню установщика: `tessera` → **S) Settings** →
**2) Plugins by URL**. Скачивать сборку заново не нужно: установщик перепишет `policy.json`,
переключит CSP в конфиге nginx и перезагрузит nginx. После этого обновите страницу
UI. Без меню: `TESSERA_ALLOW_REMOTE_PLUGINS=1 bash ~/tessera/deploy/install.sh --plugins-policy`.

### Обновление

Кнопка **Update** — горячая перезагрузка манифеста без F5. Что она *не* делает:
не перезагружает уже импортированный модуль (браузер кэширует `import()`
по URL) и не переопределяет Custom Elements. Если изменился код, нужен **F5**
(или новое имя файла с хешем); после обновления UI показывает плашку
**Перезагрузить**. Подробнее — в
[plugin-development.md](plugin-development.md#чего-не-происходит-при-update).

### Выключение и удаление

Выключатель в списке установленных плагинов снимает вклады и гарды без
удаления записи; удаление убирает запись из `mpu:v2:plugins`. Встроенные плагины нельзя
отключить или удалить.

## Безопасность и доверие

- У плагина **полный** доступ к `api.moonraker()` (в том числе к G-code и
  отключению питания): рантайм-песочницы и гранулярных разрешений нет.
  Устанавливайте только то, чему доверяете. Для install-по-URL хост требует
  явного подтверждения.
- Плагин исполняется в контексте страницы хоста: он видит `localStorage` своего
  origin (включая токены авторизации Moonraker). Ставьте плагины только из
  доверенных источников.
- Целостность проверяется **при доставке**: `deploy/tessera-ext.py` сверяет каждый
  архив с sha256 из `registry.json`. Доверие к плагину из реестра держится на ревью
  его исходников в репозитории-реестре и на сборке в CI. Браузер хеши повторно не
  проверяет, а плагины, установленные по URL, не проверяются вовсе.
- CSP, который выставляет `install.sh` (см. «По URL»), — серверный барьер против
  чужих скриптов. Диалог подтверждения в UI барьером не является.
- Гарды — удобство и защита от ошибок пользователя в UI, а не граница безопасности.

## Служба `tessera-ext`: установка из UI

Tessera по-прежнему работает без собственного бэкенда: UI — статика, данные — в
Moonraker. Служба — необязательное исключение ради одного удобства: ставить плагины без
терминала. Браузер не может записать файл на сервер, и Moonraker в `extensions/` не пишет.

- **Процесс есть только во время работы.** `tessera-ext.socket` слушает
  `/run/tessera-ext.sock`, systemd запускает `deploy/tessera-ext.py serve` при первом
  запросе, через 5 минут простоя процесс завершается.
- **Клиент передаёт только id плагина.** `POST /tessera-api/v1/{install,update,remove}`
  с телом `{"id": "acme/hello"}`, плюс `GET /tessera-api/v1/status`. URL, пути и `--force`
  через API не передать. Адрес реестра служба берёт сама и читает его только по `https://`
  (`TESSERA_REGISTRY_URL` на неё не действует; ветка — из `tessera-ext branch`).
- **Права проверяет Moonraker.** На каждый запрос служба пересылает `Authorization`,
  `X-Api-Key`, `X-Real-IP` и `X-Forwarded-For` в `GET /access/user`. Не 200 — отказ. JWT,
  API-ключи, `trusted_clients` и `force_logins` работают так же, как у Moonraker. Если
  авторизации в Moonraker нет, плагины реестра может ставить и удалять любой в сети; тем,
  кто и так управляет принтером, это не даёт ничего нового, а произвольный код так не
  поставить.
- **Защита от чужих сайтов.** POST-запросам нужен `Content-Type: application/json`, `Origin`,
  если он есть, должен совпадать с `Host`, CORS-заголовков нет.
- **Песочница.** Служба работает от пользователя принтера, не от root. Сокет открыт только
  для группы nginx. Записывать служба может только в `extensions/`: `ProtectHome=tmpfs`,
  `ProtectSystem=strict`, `NoNewPrivileges`.

Проверки архива те же, что в CLI: это один и тот же код. Журнал:
`journalctl -u tessera-ext`.

Выключается в меню: `tessera` → **S) Settings** → **3) Plugins from UI** (или
`TESSERA_UI_INSTALL=0` при установке): юниты удаляются, nginx отвечает на
`/tessera-api/` 502, и UI этот блок не показывает.

## Установка хоста: `deploy/install.sh`

Скрипт для Armbian/Debian: скачивает готовую сборку, настраивает nginx (включая
`/extensions/` и проксирование WebSocket), службу `tessera-ext` и, при желании, конфиги
Klipper. На принтере ничего не собирается: Vite и Node.js там не нужны. Он запускается как
меню в стиле kiauh:

```bash
curl -fsSL https://raw.githubusercontent.com/idex-eclipse/tessera/main/deploy/install.sh \
  -o /tmp/tessera-install.sh && bash /tmp/tessera-install.sh
```

После установки то же меню открывает команда `tessera`.

| Пункт | Что делает |
|---|---|
| **1) Install** | спрашивает каталог, порт nginx, адрес Moonraker, каталог конфигов Klipper; ставит зависимости (`curl`, `tar`, `nginx`, `python3`), скачивает сборку, настраивает nginx и Klipper, создаёт команды `tessera` и `tessera-ext` |
| **2) Update** | показывает установленный коммит и коммит опубликованной сборки ветки. *Update Tessera* — скачивание → nginx → конфиг Klipper, без вопросов. *Reinstall* — скачать сборку заново, даже если она актуальна, и переписать конфиг nginx |
| **3) Remove** | показывает, что будет удалено, и просит подтверждения: сайт nginx и его логи, `[include tessera-shell.cfg]` из `printer.cfg` (резервная копия — `printer.cfg.tessera-bak`) и `tessera-shell.cfg`, команды `tessera`/`tessera-ext`, юниты службы, каталог установки, `install.conf` и upgrade-map nginx, если его не использует другой сайт. Установленные расширения можно сохранить — они переносятся в `~/tessera-extensions-backup`. Пакеты (nginx, python3) и графики `shapers/` не удаляются |
| **S) Settings** | ветка (список веток с опубликованной сборкой; после смены предлагается Update), плагины по URL и установка из UI (применяются сразу) |
| **E) Extensions** | менеджер расширений `tessera-ext` |

Навигация как в kiauh: буква или цифра, затем Enter. Каждое действие выполняется
отдельно: ошибка завершает действие и возвращает в меню.

Настройки хранятся в `~/.config/tessera/install.conf` (`KEY=value`). Update берёт
их оттуда и ничего не спрашивает. Если файла нет (установка, сделанная до появления
меню), значения определяются по системе: ветка — по `build-info` или git, порт и
Moonraker — по конфигу nginx, плагины по URL — по `policy.json`.

**Откуда берётся сборка.** CI (`.github/workflows/build.yml`) на каждый push в `main` и
`dev` собирает UI и обновляет плавающий релиз `build-<ветка>`: архив
`tessera-<коммит>.tar.gz` и `build-info` с его именем и sha256. Установщик проверяет
sha256 и заменяет `host/`, `deploy/` и `build-info`; при сбое остаётся прежняя версия.
**`extensions/` в архив не входит и при обновлении не затрагивается.** Sha256 защищает от
повреждения при скачивании; подлинность, как и раньше, держится на GitHub и HTTPS.

**Старые установки** (git-checkout) обновляются в два шага. Первый `tessera update`
выполняет ещё старый скрипт: git, `npm ci`, сборка. Следующий видит `.git`, спрашивает
подтверждение и заменяет исходники готовой сборкой; `extensions/` и настройки остаются.
Node.js автоматически не удаляется: если он больше ни для чего не нужен, удалите его сами.

Собрать архив для форка или офлайн-установки:

```bash
npm ci && npm run build && bash tools/pack-release.sh   # → release/tessera-<коммит>.tar.gz
TESSERA_ARCHIVE=release/tessera-<коммит>.tar.gz bash deploy/install.sh install
```

Без меню (скрипты, CI):

```bash
bash install.sh install | update | reinstall | remove | extensions
TESSERA_NO_PROMPT=1 bash install.sh      # без терминала и вопросов: установка или обновление
```

Переменные окружения имеют приоритет над `install.conf`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `TESSERA_DIR` | `~/tessera` | каталог установки (внутри — `extensions/`) |
| `TESSERA_BRANCH` | `main` | ветка |
| `TESSERA_PORT` | `8000` | порт nginx |
| `TESSERA_MOONRAKER` | `127.0.0.1:7125` | адрес Moonraker |
| `TESSERA_REPO` | основной репозиторий | форки |
| `TESSERA_KLIPPER_CFG` | `~/printer_data/config` | каталог конфигов Klipper |
| `TESSERA_KLIPPER_DIR` | `~/klipper` | для обнаружения `gcode_shell_command` |
| `TESSERA_SKIP_KLIPPER_CFG` | `0` | не трогать конфиг Klipper |
| `TESSERA_SKIP_NGINX` | `0` | не настраивать nginx |
| `TESSERA_NO_PROMPT` | `0` | не задавать вопросов |
| `TESSERA_ALLOW_REMOTE_PLUGINS` | прежний выбор (при первой установке `0`) | `1` — разрешить установку по URL (без CSP); `0` — только `/extensions/` |
| `TESSERA_UI_INSTALL` | прежний выбор (при первой установке `1`) | `1` — установка плагинов из UI (служба `tessera-ext`); `0` — только CLI |
| `TESSERA_ARCHIVE` | нет | ставить из этого файла, а не из опубликованной сборки |

Скрипт не запускается от root. При каждой установке и обновлении он пересобирает
`extensions/index.json`. Подробности — в самом `deploy/install.sh`.

## Чек-лист публикации плагина

1. Собрать (`vite build`): один ES-модуль, имя = `manifest.entry`, зависимости
   внутри, `process.env.NODE_ENV` определён.
2. Положить `manifest.json` + собранные файлы в `extensions/<имя>/`.
3. Увеличить `version`.
4. `tessera-ext sync` (в dev-checkout: `node tools/extensions-sync.cjs`).
5. Settings → Plugins → Refresh → Install / Update.
6. F5, если менялся код.
7. Проверить обе темы, оба языка, offline, *Klippy not ready*.

### Публикация в реестр

Реестр — репозиторий [tessera-ext](https://github.com/idex-eclipse/Tessera-Ext). В нём
лежат и **исходники** плагинов (`plugins/<имя>/`), и собранные из них **архивы**
(`registry/`), поэтому каждый опубликованный архив можно сверить с открытым кодом.
Архивы лежат рядом с `registry/registry.json` и скачиваются оттуда же
(raw.githubusercontent.com), релизы не нужны.

Плагины разрабатываются в `Tessera-Ext/plugins/<имя>/`, а рядом с репозиторием лежит
Tessera (`…/Tessera` и `…/Tessera-Ext`). `npm run dev` там пересобирает плагин при
изменениях и копирует результат в `Tessera/extensions/<имя>/`, который раздаёт
dev-сервер. Версия публикуется из папки плагина:

```bash
npm run pack       # собственный скрипт плагина (см. plugins/spoolman), который вызывает:
node <Tessera>/tools/registry-pack.cjs dist --dir hello --url-base . --out <Tessera-Ext>/registry
```

Скрипт кладёт `registry/hello-<version>.tar.gz` и добавляет или заменяет запись
плагина в `registry/registry.json`:

```json
{ "schema": 1, "plugins": [ {
  "id": "acme/hello", "dir": "hello", "name": "Hello", "version": "1.2.0",
  "pluginApi": "0.8", "url": "hello-1.2.0.tar.gz",
  "sha256": "…", "size": 12345, "description": "…", "author": "…" } ] }
```

`pluginApi` берётся из `manifest.pluginApi` (без поля — наследное `1`); `--plugin-api`
только проверяет, что он ожидаемый. CLI отказывается ставить несовместимую запись. Для упаковки нужен GNU tar (`--sort=name`).

Архив воспроизводим на любой ОС: записи отсортированы, время и владелец обнулены, в
заголовке gzip нет времени, а байт ОС зафиксирован. Любой может пересобрать плагин из проверенного коммита и получить
тот же sha256. `--url-base .` оставляет URL архивов относительными к
`registry.json`; полный URL (например, ссылка на GitHub Release) нужен, если архивы
лежат в другом месте.

Затем закоммитьте архив вместе с `registry.json`: CLI отказывается ставить архив,
чей sha256 не совпадает с индексом. Принтеры получают новую версию командой
`tessera-ext update --all` (или через меню), пользователи перезагружают страницу UI.

Планируемый процесс в реестре: автор присылает PR, в котором закреплён коммит его
исходников; ревьюер читает diff; после merge CI делает checkout этого коммита,
собирает, запускает `registry-pack.cjs` и коммитит архив и `registry.json`.
