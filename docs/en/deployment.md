# Delivering and installing plugins

Core plugins (`@core/…`) are built into the host bundle. Remote plugins are
delivered as files on the host's server — by analogy with `klippy/extras` in
Klipper: you drop the files into a folder and the host finds them.

Delivery consists of four layers:

| Layer | What it does | Where |
|---|---|---|
| **Provisioning** | the plugin's files lie on the server | `<project>/extensions/<name>/` |
| **Discovery** | the list of available plugins | `/extensions/index.json` (a static file) |
| **Loading** | fetch the manifest → import the module | the host's plugin loader |
| **Enablement** | whether the plugin is enabled, on which printers | `localStorage` → `mpu:v2:plugins` |

The browser itself does not write files to the server: the source of truth is the
content of `extensions/`. Files get there in one of three ways:

- **from the registry, in the UI**: Settings → Plugins → **Plugin registry**. It works
  through the [`tessera-ext` service](#the-tessera-ext-service-installing-from-the-ui);
- **from the registry, in a terminal**: the `tessera-ext` command. The same reviewed
  prebuilt archives, checked against sha256;
- **by hand**: you copy a plugin folder into `extensions/<name>/` and run
  `tessera-ext sync` (in a dev checkout: `node tools/extensions-sync.cjs`). For
  development and private plugins.

## Provisioning

```
extensions/
├── index.json                  ← generated by tessera-ext sync
├── hello/
│   ├── manifest.json
│   ├── index.js                ← entry (the name comes from manifest.entry)
│   └── assets/…                ← any static files of the plugin
└── another-plugin/
    ├── manifest.json
    └── …
```

Rules:

- The folder name is arbitrary, but it is convenient to make it match the plugin's
  short name (it ends up in the manifest URL as `/extensions/<name>/manifest.json`).
- `manifest.json` is mandatory, with the fields `id`, `name`, `version`, `entry`.
- `entry` is resolved **relative to the manifest URL**: `"entry": "index.js"` →
  `/extensions/hello/index.js`. An absolute URL and a root-relative path are also
  allowed.
- The `icon` field in the manifest is optional; the script passes it through to the
  catalog record.

### From the plugin registry (recommended)

Reviewed plugins are published in a separate registry repository,
[tessera-ext](https://github.com/idex-eclipse/Tessera-Ext): a prebuilt `.tar.gz` per
version plus `registry.json` with the archives' sha256 (how it is filled: see
[Publishing to the registry](#publishing-to-the-registry)). Nothing is built on the printer: the CLI downloads the archive, checks the
hash and unpacks it into `extensions/<dir>/`:

```bash
tessera-ext                     # interactive menu: number = install / update / remove
tessera-ext list                # registry plugins + installed state
tessera-ext install hello       # download → sha256 → extensions/hello/
tessera-ext update --all        # or: update hello
tessera-ext remove hello
tessera-ext branch dev          # registry branch (also in the menu: S) Settings)
```

`deploy/install.sh` creates the `tessera-ext` command (`/usr/local/bin/tessera-ext`).
It runs [`deploy/install-ext.sh`](../../deploy/install-ext.sh), which runs
`deploy/tessera-ext.py` from the installation directory (system `python3` ≥ 3.7, standard
library only, no virtualenv). A plugin can be named by its
full id (`acme/hello`) or its short name (`hello`); an ambiguous name is an error.
Without the command (for example, before updating Tessera) use
`bash ~/tessera/deploy/install-ext.sh`. At the end, `install.sh` offers to open the
menu right away.

The CLI regenerates `index.json` itself. Then use Settings → Plugins → Refresh → Install.

What the CLI checks before anything lands in `extensions/`:

- the archive's sha256 matches `registry.json`;
- the archive contains only regular files and folders: no symlinks, no absolute
  paths, no `..`;
- the archive is at most 20 MB and unpacks to at most 100 MB and 5000 entries;
- `manifest.json` from the archive has the same `id`/`version` as the registry entry;
- `pluginApi` of the entry fits the host: same MAJOR, MINOR not above the host's (now `0.11`;
  see [plugin-development.md](plugin-development.md#plugin-api-version)). The integer `1`
  of older entries means `0.7`;
- its [dependencies](plugin-development.md#dependencies) fit: plugins from `requires` are
  installed first, an installed one older than `dependencies` asks is updated; the CLI
  refuses when the registry has no fitting version, or when a `@core/*` plugin of this
  Tessera (`host/dist/core-plugins.json` of the build) is older than needed.

A plugin is unpacked into a hidden staging folder and swapped in with `rename`. A
failed update leaves the previous version in place. Registry plugins get an
`.tessera-origin.json` file next to the manifest. The CLI refuses to overwrite a
folder you put there by hand unless you pass `--force`.

**Additional registries.** Besides the built-in registry you can add registries of other
authors: any `registry.json` in the same format (schema 1, see
[Publishing to the registry](#publishing-to-the-registry)) served over `https://`.

```bash
tessera-ext repo                                        # the built-in registry and the added ones
tessera-ext repo add https://example.com/registry.json  # optional second argument: a name
tessera-ext repo remove example.com
tessera-ext install hello --source example.com         # when several registries offer "acme/hello"
```

The same is in the menu (**S) Settings → Registries**) and in the UI (Settings → Plugins →
**Plugin sources**).

- **Where the list lives.** `extensions/.tessera-sources.json`, not `tessera-ext.conf`:
  the service may write `extensions/` and nothing else, and it adds registries on behalf of
  the UI. A registry is read once when added; one that is not a valid `registry.json` is not
  saved. At most 10 additional registries; a name is 1-32 characters of `a-z 0-9 . _ -`
  (`official` is the built-in registry and is reserved). A name is generated from the address
  when you do not give one.
- **One plugin, one registry.** Every plugin row shows where it comes from. The same id may be
  offered by several registries. A plugin is updated only from the registry it was installed
  from (the address is recorded in `.tessera-origin.json`); the entry of another registry is
  shown as *installed from another registry* and cannot be installed until the installed copy
  is removed. Installing an id that several registries offer needs `--source <name>` (the UI
  always sends the registry of the row).
- **Removing a registry** leaves its plugins installed and working, but they are not updated
  any more, and no other registry can take them over until you remove the plugin.
- **Dependencies** (`requires`) are taken from the registry of the plugin that needs them,
  then from the built-in one. A dependency that only a third registry has is reported as
  missing and is not installed: code never comes from a registry you did not choose for
  that plugin.
- **A registry that cannot be read** shows its error and does not hide the others.
- **Trust.** Everything that applies to the built-in registry still applies (sha256, archive
  limits, `pluginApi`, matching `id`/`version`), but these checks prove that the download is
  what the registry published, not that its owner is honest. A plugin runs inside the UI with
  full access to the printer. Add only registries whose owners you trust; the UI asks for a
  confirmation first.

**Registry branch.** The CLI reads `registry/registry.json` from the `main` branch of
`Tessera-Ext`. Another branch (for example `dev`, with versions that are not released
yet) is chosen in the menu (**S) Settings → Branch**, a list of branches from GitHub)
or with `tessera-ext branch <name>`. The choice is saved in
`~/.config/tessera/tessera-ext.conf` and does not depend on the Tessera branch.
`TESSERA_EXT_BRANCH` sets it for one run.

`TESSERA_REGISTRY_URL` overrides the registry address and the branch (`https://`,
`file://` or a local path, which is handy for testing a registry before publishing).

Serving on the server:

- **dev** (`npm run dev`): a middleware in `vite.config.ts` serves `extensions/` at
  `/extensions/...`, reading from disk on every request, with
  `Cache-Control: no-cache` for `.json` and `.js`.
- **prod**: an nginx block
  `location /extensions/ { alias <project dir>/extensions/; … }` with caching
  disabled (configured by `deploy/install.sh`).

Caching: the nginx site from `deploy/install.sh` sends `no-cache, no-store` for all of
`/extensions/`, so the browser gets fresh code on the next page load. On your own server
keep `index.json`, `manifest.json` and un-hashed `entry` files `no-cache`; files with
hashes in the name (`index-3f9a1c.js`) can be cached `immutable`.

## Discovery: the catalog

`extensions/index.json` is a **static** array generated by a script:

```bash
tessera-ext sync                # on a printer
node tools/extensions-sync.cjs  # in a dev checkout, same format
```

The command walks `extensions/*/manifest.json` and writes:

```json
[
  {
    "id": "acme/hello",
    "name": "Hello",
    "version": "1.0.0",
    "manifestUrl": "/extensions/hello/manifest.json",
    "icon": "optional",
    "description": "optional",
    "origin": "registry",
    "pluginApi": "0.10",
    "sha256": "…"
  }
]
```

`origin` is `registry` for plugins installed from the registry (they show a
*Verified* badge in the catalog) and `local` for folders put in place by hand.
Folders whose names start with `.` are ignored.

`pluginApi` is copied from the plugin manifest when it has one. The catalog uses it to
hide **Update** (and disable **Install**) for a plugin that needs a newer or another
major plugin API than this Tessera provides, and shows the reason next to the plugin.
Indexes generated by older tools lack the field; the check is then skipped. Even
then an update never removes a working plugin: the new version is validated first and,
if it cannot be loaded, the running version stays in place.

Folders without `manifest.json` are skipped with a warning; manifest parse errors
are logged and the other plugins still make it into the catalog.

Run it **after adding a plugin by hand** and when its `name`/`version` changes.
Changes to a plugin's code without a version change do not require regeneration.

The catalog is a discovery convenience, not the source of truth for loading: a
plugin missing from `index.json` can still be installed by URL.

## Installation by the user

### From the catalog

Settings → Plugins → **Refresh** (re-reads `index.json` bypassing the cache) →
**Install**. For each entry a state is shown:

| State | Condition |
|---|---|
| not installed | no record in `mpu:v2:plugins` |
| installed | a record exists, the version matches the catalog (or is not recorded) |
| update available | `installedVersion` ≠ the version in the catalog |

### From the registry, in the UI

Settings → Plugins → **Plugin registry**: **Install** downloads the plugin to the server
and enables it in this browser at once. **Update** replaces the files (the new code takes
effect after a page reload, the UI shows a notice), **Remove** deletes the files and the
record. The block is shown only when the service is available; without it everything
works as before, through `tessera-ext`. Folders put in place by hand cannot be replaced
or deleted from the UI.

**Plugin sources** (in the same block) lists the built-in registry and the added ones with
their errors, removes an added one and adds a new one by the address of its `registry.json`
(see [Additional registries](#from-the-plugin-registry-recommended)). The block is hidden when the
service is older and does not know registries (run `tessera update`). It does not depend on
`/extensions/policy.json`: that policy is about modules from other origins, and plugins of an
added registry are served from this origin like any other. A plugin from an added registry is labeled with its name instead
of the *verified* badge.

### By URL (advanced)

Only this dialog can limit a plugin to a set of printers (`printerIds`); an empty list
means all printers.

Settings → Plugins → **Add by URL (advanced)**: the host loads the manifest from the
address, shows a preview (`id`, `name`, `version`) and a trust warning (the plugin
gets full access to Moonraker). The record gets an *external* badge.

For an address on a different origin, the plugin's server must send **CORS** (for
both the manifest and the module). Plugins from `extensions/` (same origin) need no
CORS.

By default `deploy/install.sh` **blocks** this mode on the server. nginx sends
`Content-Security-Policy: script-src 'self'`, so the browser refuses to import a
module from another origin. The installer also writes `/extensions/policy.json`
(`{ "allowRemotePlugins": false }`), and the UI hides the button. Without
`policy.json` (dev server, manual setup) the button is shown.

The setting is changed in the installer menu: `tessera` → **S) Settings** →
**2) Plugins by URL**. No new download is needed: the installer rewrites `policy.json`,
toggles the CSP in the nginx config and reloads nginx. Reload the UI page afterwards.
Without the menu: `TESSERA_ALLOW_REMOTE_PLUGINS=1 bash ~/tessera/deploy/install.sh --plugins-policy`.

### Updating

The **Update** button is a hot manifest reload without F5. What it does *not* do: it
does not reload an already imported module (the browser caches `import()` by URL)
and does not redefine Custom Elements. If the code changed, you need **F5** (or a new
file name with a hash), and after an update the UI shows a **Reload** notice. Details in
[plugin-development.md](plugin-development.md#what-does-not-happen-on-update).

### Disabling and removal

The toggle in the installed-plugins list removes contributions and guards without
deleting the record; removal deletes the record from `mpu:v2:plugins`. Built-in plugins
cannot be disabled or removed.

## Security and trust

- A plugin has **full** access to `api.moonraker()` (including G-code and power-off):
  there is no runtime sandbox or granular permissions. Install only what you trust.
  For install-by-URL the host requires explicit confirmation.
- A plugin runs in the context of the host page: it sees its origin's `localStorage`
  (including Moonraker authorization tokens). Install plugins only from trusted
  sources.
- Integrity is verified **at delivery**: `deploy/tessera-ext.py` checks each archive
  against the sha256 in `registry.json`. Trust in a registry plugin rests on review
  of its source in the registry repository and on CI building it. The browser does
  not re-check hashes, and plugins installed by URL are not verified at all.
- The CSP set by `install.sh` (see "By URL") is the server-side barrier against
  foreign scripts. The confirmation dialog in the UI is not a barrier.
- Guards are a convenience and protection against user mistakes in the UI, not a
  security boundary.

## The `tessera-ext` service: installing from the UI

Tessera still works without a backend of its own: the UI is static files, the data lives
in Moonraker. The service is an optional exception for one convenience: installing plugins
without a terminal. A browser cannot write a file to the server, and Moonraker does not
write to `extensions/`.

- **A process exists only while it works.** `tessera-ext.socket` listens on
  `/run/tessera-ext.sock`, systemd starts `deploy/tessera-ext.py serve` on the first
  request, and the process exits after 5 idle minutes.
- **The client passes a plugin id (and a registry name) and nothing else.**
  `POST /tessera-api/v1/{install,update,remove}` with the body `{"id": "acme/hello"}`
  (`install` and `update` also accept `"source": "<registry name>"`), plus
  `GET /tessera-api/v1/status`. Paths, archive URLs and `--force` cannot be passed through the
  API. The service finds the registry addresses itself and reads them over `https://` only
  (`TESSERA_REGISTRY_URL` does not affect it; the branch comes from `tessera-ext branch`).
- **One exception: adding a registry.** `POST /tessera-api/v1/repo-add` takes
  `{"url": "https://…", "name": "optional"}` and `repo-remove` takes `{"name": "…"}`. This is
  the only place where an address comes from a request, so it is narrow: `https://` only, no
  login or password in the address, no `localhost` or private IP address, at most 300
  characters, and the registry must parse as a valid `registry.json` before it is saved. The
  same Moonraker check, `Origin` check and `application/json` rule apply as for installs.
- **Moonraker checks permissions.** For each request the service forwards `Authorization`,
  `X-Api-Key`, `X-Real-IP` and `X-Forwarded-For` to `GET /access/user`. Anything but 200 is
  a refusal. JWT, API keys, `trusted_clients` and `force_logins` work as they do in
  Moonraker. If Moonraker has no authorization, anyone on the network can install and remove
  registry plugins; that gives nothing new to someone who already controls the printer, and
  arbitrary code cannot be installed this way.
- **Protection from other sites.** POST requests require `Content-Type: application/json`,
  `Origin`, when present, must match `Host`, and there are no CORS headers.
- **Sandbox.** The service runs as the printer user, not root. The socket is open to the
  nginx group only. The service can write to `extensions/` only: `ProtectHome=tmpfs`,
  `ProtectSystem=strict`, `NoNewPrivileges`.

The archive checks are the same as in the CLI: it is the same code. Logs:
`journalctl -u tessera-ext`.

To turn it off, use the menu: `tessera` → **S) Settings** → **3) Plugins from UI** (or
`TESSERA_UI_INSTALL=0` when installing): the units are removed, nginx answers 502 on
`/tessera-api/`, and the UI does not show the block.

## The `tessera-update-manager` service: updating Tessera from the UI

Settings → About shows whether a newer build of the configured branch is published and has an
**Update Tessera** button. The browser cannot replace its own files, so a second small service
does it. It is separate from `tessera-ext` on purpose: replacing the UI needs write access to
the installation directory, while `tessera-ext` may write `extensions/` only.

- **Same model as `tessera-ext`.** `tessera-update-manager.socket` listens on
  `/run/tessera-update-manager.sock`, systemd starts `deploy/tessera-update-manager.py serve` on
  the first request and the process exits after 5 idle minutes. nginx proxies `/tessera-update/`.
  Moonraker checks permissions the same way (same code), POST requires `application/json`,
  `Origin` must match `Host`.
- **Almost no parameters.** `GET /tessera-update/v1/status` (add `?refresh=1` to skip
  the 10-minute cache) and `POST /tessera-update/v1/update` with the body `{}`. The branch and
  the repository come from `install.conf`; the repository is never taken from a request.
- **Switching the branch.** Settings → About has a branch selector. `GET /tessera-update/v1/branches`
  lists the branches that have a published build (the `build-<branch>` releases of the repository;
  `feature/x` appears as `feature-x`, which selects the same release). `POST /tessera-update/v1/update`
  with `{"branch": "<name>"}` installs that branch's build even if the commit is the same and saves
  `BRANCH` in `install.conf`, so `tessera update` stays on the new branch. The name is validated and its
  build must exist and pass the sha256 check; on any failure the UI and `install.conf` stay as they were.
  The same from the printer: `tessera-update-manager.py update --branch <name>`. Installations made
  before this feature have `install.conf` mounted read-only for the service: the switch then fails with a
  hint, and one `tessera update` on the printer rewrites the unit.
- **The same build as the installer.** The service downloads `build-info` and the archive of the
  rolling release `build-<branch>` over `https://` only, checks the sha256, unpacks into a
  staging folder, rejects links and unsafe paths, and only then swaps `host/`, `deploy/` and
  `build-info` (a killed update is rolled back on the next start). A failure leaves the working
  UI in place; `extensions/` is never touched.
- **Sandbox.** It runs as the printer user, not root, with `ProtectSystem=strict`,
  `ProtectHome=tmpfs` and `NoNewPrivileges`; it may write the installation directory and nothing
  else.
- **What it cannot do.** nginx, systemd units and the Klipper config need root and stay with
  `tessera update`. If a release needs such a change, its release notes say so. A source checkout
  (`.git`) is not updated from the UI: `tessera update` asks before replacing it.
- **After an update, reload the page.** The new files have new chunk names. A running
  `tessera-ext` keeps the previous `deploy/` mounted until it exits (up to 5 minutes).

**Update notices.** When the UI opens it asks both services (this one and `tessera-ext`) whether
Tessera or a registry plugin has a newer version and, if so, puts one text notice per kind
into the host notification center (source "Updates"; no links or buttons). It does this at most
once every **4 hours** by default; change it in Settings → About (1 to 168 hours, never less
than an hour, so GitHub is not asked on every page open). Each version is announced once per
browser. A plugin update that needs a newer plugin API than this Tessera provides is reported
separately ("update Tessera first"). With neither service installed nothing happens, and the
next page open tries again. The check runs on page open only, not on a timer.

Installations made before this service existed need one `tessera update` on the printer to get
the units and the nginx location. Logs: `journalctl -u tessera-update-manager`.

To turn it off: `tessera` → **S) Settings** → **4) Update from UI** (or `TESSERA_UI_UPDATE=0`):
the units are removed, nginx answers 502 on `/tessera-update/`, and the UI shows a hint to use the
`tessera` command instead.

## Installing the host: `deploy/install.sh`

A script for Armbian/Debian: downloads the prebuilt UI, configures nginx (including
`/extensions/` and WebSocket proxying), the `tessera-ext` service and, optionally, the
Klipper configs. Nothing is built on the printer: it needs neither Vite nor Node.js. It runs
as a kiauh-style menu:

```bash
curl -fsSL https://raw.githubusercontent.com/idex-eclipse/tessera/main/deploy/install.sh \
  -o /tmp/tessera-install.sh && bash /tmp/tessera-install.sh
```

After installation the `tessera` command opens the same menu.

| Item | What it does |
|---|---|
| **1) Install** | asks the directory, nginx port, Moonraker address and Klipper config directory; installs dependencies (`curl`, `tar`, `nginx`, `python3`), downloads the build, configures nginx and Klipper, creates the `tessera` and `tessera-ext` commands |
| **2) Update** | shows the installed commit and the commit of the branch's published build. *Update Tessera* — download → nginx → Klipper config, no questions. *Reinstall* — download the build again even if it is current and rewrite the nginx config |
| **3) Remove** | lists what will be removed and asks for confirmation: the nginx site and its logs, `[include tessera-shell.cfg]` in `printer.cfg` (backup: `printer.cfg.tessera-bak`) and `tessera-shell.cfg`, the `tessera`/`tessera-ext` commands, the service units (`tessera-ext`, `tessera-update-manager`), the installation directory, `install.conf`, and the nginx upgrade map unless another site uses it. Installed extensions can be kept: they are moved to `~/tessera-extensions-backup`. Packages (nginx, python3) and the `shapers/` graphs stay |
| **S) Settings** | branch (list of branches with a published build; Update is offered after a change), plugins by URL, installing plugins from the UI and updating Tessera from the UI (applied at once) |
| **E) Extensions** | the `tessera-ext` plugin manager |

Navigation works like kiauh: type a letter or number, then press Enter. Each action
runs on its own: an error ends the action and returns to the menu.

Settings are stored in `~/.config/tessera/install.conf` (`KEY=value`). Update reads
them and asks nothing. Without the file (an installation made before the menu
existed), values are detected from the system: branch from `build-info` or git, port and
Moonraker from the nginx config, plugins by URL from `policy.json`.

**Where the build comes from.** On every push to `main` and `dev`, CI
(`.github/workflows/build.yml`) builds the UI and updates the rolling release
`build-<branch>`: the archive `tessera-<commit>.tar.gz` and `build-info` with its name and
sha256. The installer checks the sha256 and replaces `host/`, `deploy/` and `build-info`; a
failure leaves the previous version in place. **`extensions/` is not in the archive and an
update does not touch it.** The sha256 protects against a damaged download; authenticity
rests on GitHub and HTTPS, as before.

**Older installations** (a git checkout) update in two steps. The first `tessera update` is
still run by the old script: git, `npm ci`, build. The next one sees `.git`, asks for
confirmation and replaces the sources with the prebuilt UI; `extensions/` and the settings
stay. Node.js is not removed automatically: remove it yourself if nothing else needs it.

To build an archive for a fork or an offline install:

```bash
npm ci && npm run build && bash tools/pack-release.sh   # → release/tessera-<commit>.tar.gz
TESSERA_ARCHIVE=release/tessera-<commit>.tar.gz bash deploy/install.sh install
```

Without the menu (scripts, CI):

```bash
bash install.sh install | update | reinstall | remove | extensions
TESSERA_NO_PROMPT=1 bash install.sh      # no terminal, no questions: install or update
```

Environment variables override `install.conf`:

| Variable | Default | Meaning |
|---|---|---|
| `TESSERA_DIR` | `~/tessera` | installation directory (`extensions/` is inside) |
| `TESSERA_BRANCH` | `main` | branch |
| `TESSERA_PORT` | `8000` | nginx port |
| `TESSERA_MOONRAKER` | `127.0.0.1:7125` | Moonraker address |
| `TESSERA_REPO` | upstream repo | forks |
| `TESSERA_KLIPPER_CFG` | `~/printer_data/config` | Klipper config directory |
| `TESSERA_KLIPPER_DIR` | `~/klipper` | used to detect `gcode_shell_command` |
| `TESSERA_SKIP_KLIPPER_CFG` | `0` | do not touch the Klipper config |
| `TESSERA_SKIP_NGINX` | `0` | do not configure nginx |
| `TESSERA_NO_PROMPT` | `0` | ask no questions |
| `TESSERA_ALLOW_REMOTE_PLUGINS` | previous choice (`0` on first install) | `1` = allow install by URL (no CSP); `0` = only `/extensions/` |
| `TESSERA_UI_INSTALL` | previous choice (`1` on first install) | `1` = install plugins from the UI (the `tessera-ext` service); `0` = CLI only |
| `TESSERA_UI_UPDATE` | previous choice (`1` on first install) | `1` = update Tessera from the UI (the `tessera-update-manager` service); `0` = `tessera` command only |
| `TESSERA_ARCHIVE` | none | install from this file instead of the published build |

The script does not run as root. Every install and update regenerates
`extensions/index.json`. Details are in `deploy/install.sh` itself.

## Plugin publishing checklist

1. Build (`vite build`): one ES module, name = `manifest.entry`, dependencies
   inside, `process.env.NODE_ENV` defined.
2. Put `manifest.json` + the built files into `extensions/<name>/`.
3. Bump `version`.
4. `tessera-ext sync` (in a dev checkout: `node tools/extensions-sync.cjs`).
5. Settings → Plugins → Refresh → Install / Update.
6. F5 if the code changed.
7. Check both themes, both languages, offline, *Klippy not ready*.

### Publishing to the registry

The registry is the [tessera-ext](https://github.com/idex-eclipse/Tessera-Ext)
repository. It holds both the plugin **sources** (`plugins/<name>/`) and the
**archives** built from them (`registry/`), so every published archive can be checked
against open code. Archives sit next to `registry/registry.json` and are downloaded
from the same place (raw.githubusercontent.com), so no releases are needed.

Plugins are developed in `Tessera-Ext/plugins/<name>/` with a Tessera checkout next to
the repository (`…/Tessera` and `…/Tessera-Ext`). `npm run dev` there rebuilds on
change and copies the result into `Tessera/extensions/<name>/`, which this dev server
serves. A version is published from the plugin folder:

```bash
npm run pack       # the plugin's own script (see plugins/spoolman), which runs:
node <Tessera>/tools/registry-pack.cjs dist --dir hello --url-base . --out <Tessera-Ext>/registry
```

It writes `registry/hello-<version>.tar.gz` and adds or replaces the plugin's entry
in `registry/registry.json`:

```json
{ "schema": 1, "plugins": [ {
  "id": "acme/hello", "dir": "hello", "name": "Hello", "version": "1.2.0",
  "pluginApi": "0.8", "requires": ["@core/calibrations"],
  "dependencies": { "@core/calibrations": "3.0.0" }, "url": "hello-1.2.0.tar.gz",
  "sha256": "…", "size": 12345, "description": "…", "author": "…" } ] }
```

`pluginApi` comes from `manifest.pluginApi` (a manifest without it gets the legacy `1`);
`--plugin-api` only checks that it is the expected one. The CLI refuses an incompatible entry.
`requires` lists every plugin it depends on (owners of the points in `extensions` and the
keys of `manifest.dependencies`); `dependencies` is `manifest.dependencies` as is. They are
separate fields because older CLIs accept only strings in `requires`.
Packing needs GNU tar (`--sort=name`).

The archive is reproducible on any OS: entries are sorted, timestamps and owners are
zeroed, and the gzip header has no timestamp and a fixed OS byte. Anyone can rebuild a plugin from the reviewed
commit and get the same sha256. `--url-base .` keeps archive URLs relative to
`registry.json`; pass a full URL (for example a GitHub Release download URL) to host
archives elsewhere.

Then commit the archive together with `registry.json`: the CLI refuses an archive
whose sha256 differs from the index. Printers get the new version with
`tessera-ext update --all` (or the menu), and users reload the UI page.

**Your own registry.** Anyone can publish a registry of their own: put `registry.json` and the
archives next to it on any `https://` host (GitHub raw or Pages, a web server) and give users
the address; they add it with `tessera-ext repo add <address>` or in Settings → Plugins →
Plugin sources (see [Additional registries](#from-the-plugin-registry-recommended)). The format
and the checks are the same as above; `id` must be unique within your registry, and a plugin
whose `id` also exists elsewhere is installed only on an explicit choice of the registry.
Entries with `@core/*` ids are refused.

Planned registry workflow: an author opens a PR that pins their plugin's source
commit; a reviewer reads the diff; after merge, CI checks out that commit, builds it,
runs `registry-pack.cjs` and commits the archive and `registry.json`.
